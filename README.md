# Metadata & Provenance for LLM-derived Knowledge

A demo built for the **GOBLIN Hackathon on Metadata and Provenance for Knowledge Graphs**, held in **Oviedo on 8–9 June 2026**, by the working group **Metadata & Provenance for LLM-derived Knowledge**.

The group's goal is to develop **RDF 1.2-based approaches for annotating and tracking the provenance of (parts of) knowledge graphs extracted or generated by Large Language Models (LLMs)**. This repository contains a working pipeline that demonstrates one such approach end-to-end.

## 1. Idea

Large Language Models (LLMs) are increasingly used to facilitate access to knowledge through natural language interfaces. However, despite their remarkable capabilities, they suffer from well-known limitations such as hallucinations, lack of grounding, and limited transparency regarding how generated information is produced. In critical domains such as healthcare, food, and sustainability, where trustworthiness is essential, these limitations can significantly affect the reliability of AI-driven systems.

To address these issues, recent research has increasingly combined LLMs with Knowledge Graphs (KGs). By providing structured, machine-readable representations of entities and their relationships, KGs help ground LLM outputs and reduce hallucinations. Existing KG-AI approaches, including Retrieval-Augmented Generation (RAG), GraphRAG, and Knowledge Graph Question Answering (KGQA), primarily use the KG as a source of knowledge to support answer generation.

This project addresses the complementary problem of knowledge acquisition. Rather than using a KG to support an LLM, we leverage the extraction capabilities of LLMs to enrich a Knowledge Graph with new knowledge derived from unstructured textual documents. This approach offers an opportunity to overcome one of the main limitations of many knowledge graphs: their dependence on costly manual curation and their difficulty in evolving as new information becomes available.

However, automatically incorporating LLM-generated knowledge into a KG introduces significant trustworthiness challenges. Generated statements may be unsupported by the source text, inconsistent with the ontology, duplicated, or entirely hallucinated. Furthermore, once a triple is inserted into a graph, it is often difficult to determine which document supports it, which text fragment was used, which model generated it, whether it has been validated, and how it entered the graph. Without this information, AI-generated knowledge becomes difficult to inspect, reproduce, audit, and ultimately trust.

For this reason, provenance and traceability are treated as first-class components of the knowledge acquisition process. Rather than validating knowledge after graph construction, this work integrates provenance generation, validation, and repair directly into the augmentation pipeline.

The proposed framework focuses on controlled A-Box augmentation. It allows the creation of new individuals and instance-level assertions while preserving the existing ontology. The LLM must reuse the classes, properties, and controlled concepts already defined in the KG and cannot introduce new schema elements. Candidate assertions are enriched with machine-readable provenance metadata describing the source document, supporting text chunk, generation activity, producing model, validation status, and other information relevant to LLM-generated knowledge.

To support this process, the framework exploits RDF 1.2, whose statement-level annotations simplify the representation of provenance metadata directly attached to generated assertions. Source chunks are modelled as explicit resources, enabling every generated statement to be traced back to the exact evidence from which it was derived. Provenance, therefore, becomes part of the knowledge itself rather than external documentation.

A SHACL validation agent evaluates both the generated assertions and their associated metadata. Non-conformant outputs enter a repair loop, while only validated assertions are integrated into the KG. The framework is demonstrated using the FoCosa food and health knowledge graph. Our implementation shows that RDF 1.2 annotations, provenance metadata, and SHACL validation can be successfully combined within a single provenance-aware pipeline, supporting transparent, auditable, and explainable knowledge graph augmentation through LLMs.


## 2. This demo

This repository is a **single-binary Rust pipeline** that drives an LLM through an RDF 1.2 + SHACL extraction-and-validation loop using the **`rudof` MCP server**.

### 2.1 What it does in one paragraph

Given (a) an ontology, (b) a SHACL shapes file describing the required provenance pattern, and (c) a textual corpus, the pipeline asks an LLM to extract new A-Box assertions about food items and their suitable diets, annotate each assertion with **RDF 1.2 statement-level provenance** (which LLM produced it, which document it came from, how it was validated), and **validate the result against SHACL inside a tool-calling loop**. Only a fully conforming graph is emitted. A final independent verification pass produces a conformance report.

### 2.2 Inputs and outputs

| Path | Role |
| --- | --- |
| `inputs/gold_standard_GOBLIN.owl` | Ontology + a small seed A-Box (FoCosa food/health vocabulary) |
| `inputs/shapes/provenance_shapes.ttl` | SHACL shapes — require RDF 1.2 reified provenance on every `schema:suitableForDiet` assertion |
| `inputs/food_diet_expansion.txt` | Source corpus: short paragraphs describing diet suitability of common foods |
| `outputs/extracted_kg.ttl` | Final, SHACL-conformant Turtle-star graph produced by the LLM |
| `outputs/conformance_report.ttl` | SHACL validation report from the **independent** post-hoc verification run |

The provenance shape (`inputs/shapes/provenance_shapes.ttl`) requires every `schema:suitableForDiet` edge from a `focosa-f:FoodItem` to carry an RDF 1.2 reifier with three properties:

- `llm:LLM_id` — which model produced the statement,
- `llm:validationMethod` — how it was validated (`"shacl"`),
- `ctx:extractedFrom` — the IRI of the source document.

### 2.3 Pipeline — step by step

The pipeline is implemented in `src/pipeline.rs` and uses three pieces:

- `src/mcp.rs` — a thin client that spawns `rudof mcp` as a child process and speaks the **Model Context Protocol** to it.
- `src/llm.rs` — an OpenAI-compatible tool-calling loop (works with Qwen and DeepSeek endpoints).
- `src/pipeline.rs` — the orchestration.

The flow is:

1. **Spawn `rudof mcp`.** A child process is launched and the MCP `initialize` handshake is completed. `rudof`'s RDF tooling (`load_rdf_data_from_sources`, `validate_shacl`, `execute_sparql_query`, `export_rdf_data`, …) is now exposed as MCP tools.

2. **Pre-load the ontology + seed A-Box** into the MCP datastore by calling `load_rdf_data_from_sources`. The LLM does not need to (and must not) re-load it.

3. **List MCP tools** and re-shape them into OpenAI function-tool schemas so the LLM can call them through a standard tool-calling chat completion.

4. **Build the prompts** (`src/llm.rs`):
   - The **system prompt** enforces a strict workflow: (i) compose candidate Turtle with RDF 1.2 `{| ... |}` annotations, (ii) call `load_rdf_data_from_sources`, (iii) call `validate_shacl`, (iv) repair on violations, (v) emit a final fenced Turtle block **only** when `sh:conforms true`.
   - The **user prompt** carries the source text, the existing KG, the document IRI to use verbatim in every `ctx:extractedFrom`, the RDF 1.2 provenance pattern, the SHACL metadata shape, and a long list of A-Box-only constraints (no new classes, no new predicates, no inferred facts, no duplicates).

5. **Run the extraction loop.** Each LLM turn that emits `tool_calls` is forwarded transparently to `rudof` via MCP and the tool result is fed back into the conversation. The loop is bounded by `--max-tool-calls` (default 30). The LLM is therefore free to iterate: load → validate → read violations → patch → reload → re-validate, until SHACL conforms.

6. **Capture the final answer.** When the LLM returns a message with no tool calls, the pipeline extracts the fenced ` ```turtle ` block. If the model forgot to include it, the pipeline falls back to `export_rdf_data` on the MCP datastore so the cumulative loaded graph is preserved.

7. **Independent verification.** The first MCP process is shut down and a **fresh** `rudof mcp` is spawned. The just-written `outputs/extracted_kg.ttl` is loaded into the clean datastore and validated against the same SHACL shapes. This guarantees the report reflects only the final artefact, not any state the LLM accumulated mid-loop. The report is written to `outputs/conformance_report.ttl`.

### 2.4 Why `rudof` via MCP

[`rudof`](https://github.com/rudof-project/rudof) is the RDF/SHACL/ShEx toolkit used here. Exposing it through **MCP** means the LLM **does not need to know how to "do" RDF** — it just calls tools (`load_rdf_data_from_sources`, `validate_shacl`, …) the same way it would call any function tool. The repair loop is then *driven by real SHACL feedback from a real validator*, not by the model's own guess about whether its output is well-formed. This is the core mechanic that lets a small Rust binary plus a generic LLM produce a guaranteed-conformant, fully provenance-annotated RDF 1.2 graph.

## 3. Running the demo

### 3.1 Prerequisites

- **Rust** (stable, edition 2021).
- **`rudof`** binary, built with MCP support. The default path is `/home/samu/.local/bin/rudof`; override with `--rudof-bin` or `RUDOF_BIN`.
- An **OpenAI-compatible API key** for one of the supported providers:
  - **Qwen** (DashScope OpenAI-compatible endpoint) — `QWEN_API_KEY`, optional `QWEN_BASE_URL`, `QWEN_MODEL`.
  - **DeepSeek** — `DEEPSEEK_API_KEY`, optional `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`.

### 4.2 Build & run

```bash
cargo build --release

export QWEN_API_KEY=...            # or DEEPSEEK_API_KEY=...
export RUDOF_BIN=/path/to/rudof

./target/release/hackathon_metadata_provenance_kg --model qwen --ontology inputs/gold_standard_GOBLIN.owl --shapes inputs/shapes/provenance_shapes.ttl --corpus inputs/food_diet_expansion.txt --out-kg outputs/extracted_kg.ttl --out-report outputs/conformance_report.ttl --max-tool-calls 30
```

All path flags have sensible defaults (see `src/cli.rs`), so the minimal invocation is just `--model qwen` (or `--model deepseek`).

### 4.3 Expected outputs

- `outputs/extracted_kg.ttl` — Turtle-star A-Box additions, every new `schema:suitableForDiet` carrying an RDF 1.2 reifier with `llm:LLM_id`, `llm:validationMethod`, and `ctx:extractedFrom`.
- `outputs/conformance_report.ttl` — SHACL validation report from the independent verification pass; should report `sh:conforms true`.

## Warning — vibe-coded hackathon implementation

This implementation has been **mainly "vibe-coded"** under the time pressure of the GOBLIN Hackathon (8–9 June 2026, Oviedo). The pipeline works end-to-end on the supplied inputs and demonstrates the research idea, but the code has **not** been fully tested.

The vibe-coding took as a reference the **`ClaudeMCPConnector`** idea from [`rudof-project/LLM-KG-Bench-rudof`](https://github.com/rudof-project/LLM-KG-Bench-rudof) — specifically, the pattern of letting an LLM drive `rudof` through MCP tool calls inside a loop.
